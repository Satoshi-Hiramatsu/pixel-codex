# Pixel Codex Android コンパニオンアプリ計画書

> 実装状況（V0.3.0）：スマートフォンからの要求で、PCが開発サーバーのURL・作業フォルダ内のHTML・PC上のウィンドウを撮影し、Android側で表示できるようにした。画像はWebSocket（16KB上限・テキストのみ）に載せられないため、Relayに認証付きのHTTP経路`GET /blob/<id>?token=`を追加して受け渡している。既定はオフで、通信室で明示的に許可した場合だけ有効になる。
>
> 実装状況（V0.2.1）：ケーブルを使わないペアリング（6桁コード／QR）、Relayポートとトークンの永続化、PCのIP変更に追従するLAN内自動再検出、Androidからの承認・質問回答を実装した。Pixel 9で完全ワイヤレスの実機確認まで完了。残るのは端末鍵、FCM通知、外部Relayでの実運用。
>
> V0.2.0での実装：PC通信室、通信担当者、Remote Gateway、開発用Relay、Android Composeアプリ、Pixel 9とのUSB実機テスト。

> 方針更新：Androidからの指示送信を初期MVPの必須機能とする。既存スレッドへの追加だけでなく、PCで選択中のワークスペースに対する新規指示もAndroidから開始できる。iPhone／iOS対応は現在および将来の対象外とする。PC側のモバイル通信管理は、ゲーム内の「通信室」と「通信担当者」へ集約する。

## 1. 概要

Pixel Codexで動作中のCodexをAndroid端末から確認し、**初期版からAndroidで新規指示と追加指示を送信・実行できる**簡易コンパニオンアプリを開発する。Androidから送った指示は、PCで選択中のワークスペースに対して新規開始、即時実行、またはQueue実行される。初期版でPC操作に限定するのは、承認要求への応答とCodexからの質問への回答だけである。

### 初期版の操作可否

| 操作 | Android | PC |
| --- | --- | --- |
| 新規テキスト指示 | 可能 | 可能 |
| 既存スレッドへの追加指示 | 可能 | 可能 |
| 実行中に送った指示のQueue登録 | 自動で可能 | 可能 |
| 状態・最新メッセージ確認 | 可能 | 可能 |
| 承認要求への許可・拒否 | 可能（V0.2.1／PCで許可した場合のみ、既定オフ） | 可能 |
| Codexからの質問への回答 | 可能（同上。秘密の入力を含む質問を除く） | 可能 |
| 作りかけの画面の確認 | 可能（V0.3.0／PCで許可した場合のみ、既定オフ） | 可能 |

> V0.2.1で承認と質問回答をAndroidへ開放した。当初は「初期版ではPC操作に限定する」としていたが、外出先で承認待ちのまま止まる時間が長かったため前倒しした。既定はオフで、通信室で明示的に許可した場合だけ有効になる。

初期版からAndroidを指示入力経路の一つとして扱う。ただし「スマートフォンを小型の開発端末にする」のではなく、次の操作を外出先から短時間で行えることを目的とする。

- 処理完了、質問、承認待ち、エラーの通知を受け取る
- 実行中のスレッドとエージェント状態を確認する
- PCで選択中のワークスペースへテキスト指示を送る
- ルートスレッドがなければ新規作成して処理を開始する
- 実行中の場合は、現在の処理完了後に追加指示として送る（Queue）
- PC側で設定したタイミングと内容だけをAndroidへ通知する

Codexとの通信はAndroidから直接行わず、既存のPixel Codexデスクトップアプリを操作主体とする。

## 2. 設計方針

| 項目 | 方針 |
| --- | --- |
| Android実装 | Kotlin + Jetpack Compose |
| iOS対応 | 対象外。将来計画にも含めない |
| デスクトップ | 既存ElectronメインプロセスへRemote Gatewayを追加 |
| PC側UI | ゲーム内に通信室と常設の通信担当者を追加 |
| Codex接続 | 既存の`CodexClient`と`codex app-server`を再利用 |
| 遠隔通信 | TLS上のWebSocket。PC、Androidとも中継サービスへ外向き接続 |
| Push通知 | Firebase Cloud Messaging（FCM） |
| ペアリング | デスクトップ表示のワンタイムQRコード |
| 認証 | 端末ごとの鍵と短命アクセストークン |
| 権限 | Androidから実行できる操作を明示的にホワイトリスト化 |
| データ保持 | 中継サービスは原則として本文を永続保存しない |

Android専用の小規模アプリとしてネイティブ実装を選ぶ。iPhone／iOS対応を前提とした共通UI層やマルチプラットフォーム対応は行わない。

## 3. 対象範囲

### 最小MVPに含める機能

1. QRコードによる端末ペアリング
2. ペアリング済みPCのオンライン状態表示
3. PCで選択中のワークスペース、ルートスレッド、最新状態・最新メッセージの表示
4. Androidから選択中ワークスペースへのテキスト指示送信
5. ルートスレッドがなければ、同ワークスペースで新しいルートスレッドを作成して指示を開始
6. ルートスレッドが待機中なら、次のターンとして指示を即時送信
7. 実行中に届いた指示はQueueへ保存し、ターン完了後に一度だけ実行
8. 完了、承認待ち、質問、エラーのPush通知
9. 通信室で通知タイミングと通知内容を設定
10. 通信室でRelay接続、接続テスト、ペアリング、端末失効を管理
11. 切断後の自動再接続と未処理指示の状態確認

### Android指示の初期動作

Androidの送信ボタンは初期版から有効にする。送信後の動作はPC側の状態だけで決定し、利用者にCodexのスレッド構造を意識させない。

| PC側の状態 | 動作 |
| --- | --- |
| Codex未接続 | 送信を受け付けず、Androidへ再接続が必要と表示 |
| ワークスペース未選択 | 送信を受け付けず、PCでの選択が必要と表示 |
| ルートスレッドなし | 現在のワークスペースにルートスレッドを作成して開始 |
| ルートスレッドが待機中 | `sendTask`で即時開始 |
| ルートスレッドが実行中 | PC側の`RemoteQueue`へ保存し、完了後に開始 |

PCがオフラインの間は新しい指示をRelayへ預けない。時間が経ってから意図せず実行されることを防ぐため、送信欄を無効化して再接続後の再送を求める。

### MVPに含めない機能

- 任意のシェルコマンド実行
- Androidからのファイルシステム閲覧
- Git操作、コミット、Pushの専用UI
- 大規模なdiffレビュー
- Androidで任意ワークスペースを選択して新規スレッドを作成する機能
- 音声入力、Androidからの画像・ファイル添付（PCから端末への画面プレビューはV0.3.0で実装）
- 複数ユーザーでの共同操作
- Codex公式Remote機能とのセッション共有
- Steerによる実行中ターンへの割り込み
- Androidからの停止
- iPhone／iOS版

Steerと停止は基本操作の安全性と利用頻度を確認した後に拡張する。承認と質問回答はV0.2.1で実装した（既定オフ）。iPhone／iOS版は拡張候補にも含めない。

## 4. システム構成

```text
┌─────────────────────────────┐
│ Android Companion           │
│ Compose / Room / FCM        │
└──────────────┬──────────────┘
               │ HTTPS / WSS
               ▼
┌─────────────────────────────┐
│ Remote Relay                │
│ 認証・接続中継・Push起動      │
│ Codexの実行権限は持たない      │
└──────────────┬──────────────┘
               │ outbound WSS
               ▼
┌─────────────────────────────┐
│ Pixel Codex Desktop         │
│ 通信室 / 通信担当者           │
│ Remote Gateway              │
│ Command Guard / State Cache │
└──────────────┬──────────────┘
               │ in-process
               ▼
┌─────────────────────────────┐
│ CodexClient                 │
│ codex app-server / JSON-RPC │
└─────────────────────────────┘
```

PCへ外部公開ポートを開けない。RelayからPCへの任意コード実行も許可せず、デスクトップ側のCommand Guardが許可済み操作だけを`CodexClient`へ渡す。

### デスクトップ側

#### 通信室

Pixel Codexのオフィスに「通信室」を追加する。モバイル通信に関する表示と設定は、通常の会話画面やシステム設定へ分散させず、通信室へ集約する。

初期画面に置く項目：

- Remote通信の有効／無効
- Relay URL
- 接続状態と最終接続時刻
- 接続テストと再接続
- Androidペアリング用QRコード
- ペアリング済み端末一覧と失効
- Androidからの指示受付の有効／無効
- 画面プレビューの送信可否と、撮影対象のURL登録（V0.3.0追加）
- 通知するイベント
- 通知に含める内容のレベル
- 最近の送受信履歴

初期版のネットワーク設定は、Relay URL、通信ON/OFF、自動再接続、接続テストに限定する。プロキシ、独自証明書、LAN直結などの詳細設定は追加しない。

#### 通信担当者

通信室には常設の「通信担当者」を1名配置する。会計担当と同様のローカル専用スタッフとし、Codexスレッドやモデル利用料金は発生させない。

通信担当者の役割：

- 接続状態を見た目と発言で知らせる
- 通知対象イベントを監視する
- 設定された内容レベルへ通知文を整形する
- Androidからの指示を受信し、状態に応じて新規スレッド、即時ターン、Queueへ振り分ける
- 送信成功、保留、失敗を通信ログへ記録する

実装時には`AgentDuty`へ`communicator`を追加し、`permanent: true`、`virtual: true`のプロフィールとして扱う。AIに通知文を生成させず、初期版は決定的なテンプレートで整形する。

#### 通信ポリシー

通信室で次のポリシーを設定できるようにする。

```ts
interface CommunicationPolicy {
  enabled: boolean;
  relayUrl: string;
  autoReconnect: boolean;
  allowRemoteInstructions: boolean;
  /** V0.2.1追加。承認の可否と質問への回答を端末から返せるようにするか。 */
  allowRemoteApprovals: boolean;
  /** V0.3.0追加。端末からの要求で画面を撮って渡せるようにするか。 */
  allowRemotePreview: boolean;
  /** V0.3.0追加。撮影対象として登録した開発サーバーなどのURL。 */
  previewUrls: string[];
  events: {
    turnCompleted: boolean;
    approvalRequested: boolean;
    questionRequested: boolean;
    errorOccurred: boolean;
  };
  contentLevel: 'status-only' | 'summary' | 'final-message';
  hideSensitiveDetails: boolean;
}
```

既定値は、完了・承認待ち・質問・エラーを通知し、内容は`summary`、機密情報のマスキングは有効、Androidからの指示受付は有効とする。`allowRemoteApprovals`だけは既定で無効とする。コマンド実行の許可を手元から出せる操作であり、利用者が明示的に選んだときにだけ有効にすべきだからである。

新規モジュール候補：

```text
src/remote/
├── RemoteGateway.ts       WebSocket接続と再接続
├── RemoteProtocol.ts      メッセージ型、バージョン管理
├── RemoteStateStore.ts    モバイル向け最小状態
├── RemoteCommandGuard.ts  操作、スレッド、期限、送信間隔の検証
├── RemoteQueue.ts         Queue指示の保持と実行
├── PairingManager.ts      QR、端末鍵、失効管理
├── CommunicationPolicy.ts 通知タイミングと内容設定
├── MessageFormatter.ts    決定的テンプレートとマスキング
├── PreviewCapture.ts      画面の撮影とJPEG化（V0.3.0）
├── previewSources.ts      撮影対象の正規化と検証（V0.3.0）
└── DriveUploader.ts       Google DriveのOAuthとアップロード（V0.3.0）
```

既存の`codex.on('event')`をRemote Gatewayにも購読させる。既存Rendererの状態管理は初期段階では変更せず、モバイルに必要な最小状態だけを`RemoteStateStore`で保持する。

既存機能との対応は以下とする。

| モバイル操作 | 既存処理／追加処理 |
| --- | --- |
| 新規指示 | ルートスレッドがなければ`startThread`後に`sendTask` |
| 即時指示 | 待機中のルートスレッドへ`sendTask` |
| Queue指示 | `RemoteQueue`へ保存し、対象ターン完了後に`sendTask` |
| 状態更新 | `codex.on('event')`から生成 |

初期版ではAndroidから選べる対象を「PCで現在選択中のワークスペース」だけに限定する。指示先は常にルートスレッドとし、ルートスレッドがなければ通信担当者が作成する。サブエージェントを選択中でも通信担当者がルートスレッドへ指示を渡す。

### Relay側

Relayは以下だけを担当する。

- デスクトップとAndroidの認証
- WebSocketセッションの対応付け
- 暗号化されたイベント／コマンドの転送
- Androidがオフラインの場合の通知イベント短期キュー（AndroidからPCへの指示は保存しない）
- FCM通知の起動
- 端末失効と監査メタデータの保持

RelayにCodex、リポジトリ、ローカルファイルへアクセスする機能は持たせない。本文ログのサーバー保存も初期設定では無効にする。

│   ├── local/        Room、暗号化設定

├── domain/           Session、Command、Approval
├── notification/     FCM、通知チャネル

## 6. 通信プロトコル

すべてのWebSocketメッセージにプロトコルバージョンと一意なIDを持たせる。

```json
{
  "version": 1,
  "messageId": "uuid",
  "type": "instruction.submit",
  "hostId": "host_uuid",
  "createdAt": "2026-07-31T12:00:00Z",
  "payload": {
    "text": "現在の修正後に回帰テストも実行してください"
  }
}
```

### Androidから送るコマンド

- `instruction.submit`
- `state.snapshot.request`
- `approval.respond`（V0.2.1追加。`accept`／`decline`のみ）
- `question.respond`（V0.2.1追加。12件・1000文字まで）
- `preview.sources.request`（V0.3.0追加。撮影対象の一覧要求。2秒に1回まで）
- `preview.request`（V0.3.0追加。`sourceId`と`viewport`のみ。5秒に1回まで）
- `preview.upload`（V0.3.0追加。Driveへの受け渡し要求。5秒に1回まで）

`instruction.submit`を受信したデスクトップGatewayが、現在の状態に応じて`startThread`、`sendTask`、`RemoteQueue`のいずれかへ振り分ける。AndroidはCodexの内部メソッドを指定しない。

`approval.respond`と`question.respond`は、`requestId`がPCで表示中の要求と一致する場合だけ実行する。処理済み、または`allowRemoteApprovals`が無効なら拒否し、理由を`command.acknowledged`で端末へ返す。

### デスクトップから送るイベント

- `state.snapshot`
- `thread.updated`
- `agent.updated`
- `message.created`
- `turn.completed`
- `approval.requested`
- `question.requested`
- `error.occurred`
- `command.acknowledged`
- `host.status`
- `preview.sources`（V0.3.0追加）
- `preview.ready`（V0.3.0追加。画像そのものではなく、Relayからの相対パスだけを返す）
- `preview.failed`（V0.3.0追加）
- `preview.uploaded`（V0.3.0追加。DriveのURL）

### Google Drive連携（V0.3.0）

外部Relayが無い間、LAN外から見返せる唯一の手段として用意する。撮影のたびに自動では上げず、
端末で押されたときだけ実行する。

- 認可はデスクトップ向けOAuth。ループバック（`127.0.0.1`）とPKCEで受け、外向きの口は開かない
- 求める権限は`drive.file`のみ。**このアプリが作ったファイル**にしか届かない
- 開発者の資格情報を配布物へ埋め込まない。利用者が自分のGoogle Cloudプロジェクトで
  OAuthクライアントを作り、通信室で登録する。流出しても他の利用者へ波及しない
- クライアントシークレットと更新用トークンはElectronの`safeStorage`で暗号化して保存し、
  レンダラーへは一切返さない
- 保存先はマイドライブの`Pixel Codex Previews`フォルダ。削除は利用者が行う
- 共有設定は変更しない。端末側で同じGoogleアカウントにサインインしている前提とする

### 画面プレビュー（V0.3.0）

撮った画像はWebSocketに載せない。Relayの`maxPayload`は16KBでバイナリも拒否するため、
1枚を100通以上に割ることになり経路として成立しないからである。代わりにRelayのHTTP側へ
`GET /blob/<id>?token=`を追加し、端末はそこから取りに行く。

- 撮影対象は**PCが登録した一覧のidだけ**を端末が選ぶ。端末からURLやパスは受け取らない
- `preview.ready`が返すのはRelayからの**相対パス**だけ。PCがどのアドレスで見えているかは
  端末しか知らず、端末は接続に使っているトークンを既に持っているため、絶対URLは端末が組み立てる
- `previewId`は`randomUUID`。有効期限は10分で、過ぎたら実ファイルごと削除する
- 撮影はスマートフォンから要求されたときだけ実行する。ターン完了時の自動送信は行わない
- 撮影対象の一覧は`state.snapshot`には含めない。あれは返答が1文字進むたびに端末へ流れる
  経路であり、滅多に変わらない選択肢を混ぜても通信量が増えるだけである
- 1枚は幅1080pxまでのJPEG（品質72）へ落とす。実測でおおむね50〜150KB

各コマンドは`messageId`で重複排除する。モバイル側では送信済み、PC到達済み、Codex受付済み、完了／失敗を区別して表示する。

V0.2.1では、`allowRemoteApprovals`が有効なときに限り`state.snapshot`へ`approval`と`question`の中身を含める。`requestId`は文字列化して渡すが、これは応答の突き合わせにのみ使う識別子であり、Codexの内部メソッドやスレッド構造は公開しない。無効なときは従来どおり`approvalPending`／`questionPending`の真偽値だけを送る。

## 7. ペアリングとセキュリティ

### ペアリング手順（V0.2.1の実装）

同一ネットワーク内の開発用Relayに対する実装は次のとおり。中継サービスを使う本番手順は下段に残す。

1. Pixel Codexの通信室で`ケーブルなしでペアリング`を選択する。
2. デスクトップがLANアドレス・6桁コード・QRを表示する。有効期限は3分。
3. Androidがカメラで読み取る（アドレスとコードの手入力も可）。
4. Androidが`POST /pair`でコードを送り、一致すればRelayトークンとHost IDを受け取る。
5. コードは1回で使い切り、5回まちがえるとその場で受付を終了する。比較は`timingSafeEqual`で行う。
6. Relayのポートとトークンはデスクトップ側に永続化し、以後はアプリ起動だけで再接続する。

PCのIPが変わった場合、AndroidはLAN内の`/health`を叩いてHost IDが一致するPCを探し直す。探索対象は「前回PCがいた/24」と「端末自身の/24」の2つで、探索中にトークンは送らない。

### ペアリング手順（中継サービス利用時・未実装）

1. デスクトップが5分間有効なワンタイムQRを表示する。
2. Androidが端末鍵を生成してQRを読み取る。
3. PCとAndroidの両方に6桁の確認コードを表示する。
4. PC側で最終承認すると端末が登録される。
5. 以後は短命トークンを更新しながら再接続する。

### 必須対策

- TLS 1.2以上
- Android Keystoreで秘密鍵を保管
- デスクトップではOS資格情報ストアへ端末情報を保管
- トークンは短命化し、更新トークンを端末単位で失効可能にする
- コマンド種別、対象スレッド、状態、期限をPC側で再検証
- 1メッセージの文字数と送信頻度を制限
- 承認要求の全文に秘密情報が含まれる場合はマスキング
- Android通知にはコマンド全文やリポジトリ内容を表示しない
- アプリ復帰時に生体認証または端末認証を要求可能にする
- 公開インターネットからPCへ直接ポート転送しない

Androidからの任意シェル、任意ファイル読み取り、任意JSON-RPC呼び出しは設計段階で禁止する。初期版で許可する操作は、PCで選択中のワークスペースへのテキスト指示と状態取得だけとする。

## 8. 通知設計

通知チャネルを用途別に分ける。

| チャネル | 既定 | 表示内容 |
| --- | --- | --- |
| 承認待ち | ON・高優先度 | PC名、スレッド名、操作概要 |
| 質問 | ON・高優先度 | PC名、質問の短い要約 |
| 完了 | ON | PC名、スレッド名、最終報告の短い要約 |
| エラー | ON・高優先度 | PC名、エラー種別 |
| 進捗 | OFF | 状態変化のみ |

通知タップで対象スレッドまたは通知詳細を直接開く。承認待ちと質問にはPCでの対応が必要なことを表示する。ロック画面では機密本文を既定で隠す。

## 9. データ保持

### Android

- ホスト、スレッド、最新メッセージをRoomへキャッシュ
- 認証情報はAndroid Keystoreを利用
- 会話キャッシュは既定7日、設定で即時削除可能
- ログアウトまたはペアリング解除で鍵とキャッシュを削除

### デスクトップ

- ペアリング済み端末と失効状態をOS資格情報ストアへ保存
- 未送信Queueはアプリ再起動に備えて暗号化保存
- 監査ログには本文ではなく、時刻、端末、操作種別、結果を記録

### Relay

- 接続ルーティングと端末IDのみ保持
- オフラインキューは暗号化し、最大24時間で削除
- Push本文には機密情報を含めない

## 11. テスト方針

### 自動テスト

- ProtocolのJSON互換性とバージョンテスト
- Command Guardの許可／拒否マトリクス
- Queueの順序、重複排除、再起動復元
- ルートスレッドなし／待機中／実行中の指示振り分け
- 通知ポリシーと内容レベルごとの送信可否
- Relayの認証、再接続、複数端末分離
- Android Repository／ViewModelテスト
- Compose主要画面テスト

### 結合テスト

- Queueがターン完了後に一度だけ実行される
- ルートスレッドがない場合に現在のワークスペースで新規開始される
- 待機中は指示が即時開始される
- PCオフラインまたはワークスペース未選択時は指示が実行されない
- 通信室で無効化したイベントがAndroidへ送られない
- Androidからルートスレッド以外へ直接指示できない
- PCオフライン中のコマンドが誤実行されない
- AndroidのWi-Fi／モバイル回線切り替え後に復帰する
- Push通知から正しいスレッドを開く
- 端末失効後は即座に操作不能になる

## 12. MVP受け入れ基準

- QRペアリングが2分以内に完了する
- PCオンライン時、状態更新が通常2秒以内にAndroidへ反映される
- 完了・承認・質問・エラー通知がバックグラウンドで届く
- Androidからのテキスト指示が初期版から利用できる
- ルートスレッドがない場合でも、現在のワークスペースで新しい処理を開始できる
- Androidからのテキスト指示がルートスレッドへ重複なく実行される
- 実行中に届いた指示がQueueへ入り、ターン完了後に一度だけ実行される
- 通信室の設定どおりに通知タイミングと内容が切り替わる
- 許可されていない対象指定、期限切れメッセージ、失効端末の操作がPC側で拒否される
- PCやRelayの再起動後に手動再ペアリングなしで復旧する
- Androidから任意シェルや任意ファイルアクセスを実行できない
- 通知とRelayログにプロンプト全文や秘密情報が残らない

## 13. 主なリスクと対策

| リスク | 対策 |
| --- | --- |
| モバイル指示の対象を誤る | 初期版はPCで選択中のワークスペースと、そのルートスレッドだけに限定 |
| オフライン中の古い指示が後から実行される | PCオフライン中は指示を受け付けず、Relayにも保存しない |
| 実行中ターンへの誤割り込み | 初期版はSteerを実装せず、必ずQueueへ保存 |
| 回線断による重複指示 | `messageId`による重複排除とACK状態管理 |
| Codex App Serverのイベント仕様変更 | `RemoteProtocol`で内部イベントを正規化し、Androidと分離 |
| Relay障害 | 再接続、通知イベントだけの短期キュー、PC側Queue永続化 |
| 機密情報の外部流出 | 本文非保存、通知マスキング、暗号化、保持期間制限 |
| デスクトップRendererとの状態不一致 | GatewayがCodexイベントを直接購読し、snapshotで再同期 |
| サブエージェントへ直接指示できない | ルートスレッド経由へのフォールバック |

## 15. 着手時に確定する事項

本計画では次を初期判断としている。

- Androidのみを対象とし、Kotlin + Composeを使う。iPhone／iOSは今後も対象にしない
- 外出先利用を想定し、LAN限定ではなくRelay方式を採用する
- Relayは本文を永続保存しない
- MVPは通信室での設定、現在のワークスペースの監視、Androidからの新規／追加テキスト指示に限定する
- 一般公開ではなく、まず個人／限定テスター向けに配布する

これらを変更する場合でも、Androidとデスクトップ間の`RemoteProtocol`を安定境界にすることで影響を局所化する。
